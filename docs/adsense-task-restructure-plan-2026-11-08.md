# zoxide.org：低价值内容拒审后的任务结构改造方案

> 首页职责已由 [首页恢复与调整调研](homepage-restoration-research-2026-11-08.md) 修正：恢复完整基础指南，保留紧凑任务入口。本文其他页面的任务路径改进继续保留。

日期：2026-11-08。阶段：用户截图已确认 Needs attention / 低价值内容，已不是 Getting ready。本文是产品与内容结构方案，不是批准保证，也不代替账户侧检查。

## 结论与证据边界

采用附件里“围绕具体用户问题重组内容、提供真实实践与增量价值”的思路。不能采用其中没有官方依据的通过率、字数、相似度、自然流量、关键词密度、DR 等硬阈值。也不能由等待时间推断存在人工审核，更不能把搜索质量评估指南直接当成 AdSense 审批打分表。

本次用 Scrapling 实时读取首页、教程中心、博客中心、下载页和 zoxide-doctor，五页均为 HTTP 200。证据在 `outputs/adsense-restructure-2026-11-08/live-pages.json`。这是代表页面抽查，不是今天对全站 78 页的重新完整抓取。

关键发现：线上首页依然有 15 个 H2、Neovim 宣传和后半段重复内容；仓库仍保留 10 月 29 日那批未提交的首页、语言标签和文案修改。因此至少首页整改未在线生效，不能把此次拒审当作“Google 已看过这些修改并仍然拒绝”。上次本地 78 页验证结果也不能冒充此次线上部署验收。

## 为什么只修三个瑕疵不够

技术与配置就绪解决的是能否访问和识别站点，不能证明全站广告价值。现有站点已有实测教程和原创工具，但这些资产仍被按 Tutorials / Blog / FAQ 的出版形式组织，用户需要自行判断该看哪篇。

代表性问题：

- 首页同时提供长篇安装指南和重复的安装、教程、快速链接区块。
- 下载页也包含安装选择、配置与验证；首页与下载页需要明确各自职责。
- 教程中心把“已安装后的快速验证”和平台安装按不同分类呈现，学习顺序没有覆盖所有用户的起点。
- 命令参考、初始化与故障排查主要放在 Blog；用户要先理解内容分类再寻找解决办法。
- zoxide-doctor 页面内容已有五类真实输出和局限说明，但运行入口需要 Node.js；主页主导航没有这个工具。其原创性已经存在，下一步应提高可发现性和可用性，而不是再加一篇介绍它的文章。

以上是可检查的产品问题与推断，不是 Google 向本项目公开的逐项拒审原因。

## 新的站点承诺

为安装、配置和排错 zoxide 的用户提供经过测试的操作路径；明确区别于上游项目，保留官方来源、作者说明、测试日期、环境和能力限制。

首屏三个任务入口：

1. 第一次安装：选系统与 Shell，取得适用的安装、初始化与验证步骤。
2. 已安装但不能用：根据实际报错确定缺失的是程序、Shell 函数、历史数据还是 fzf。
3. 日常使用与配置：直接查命令、匹配规则、排除目录和数据库维护。

原创工具以清晰的独立入口展示，不再只靠页脚与长页面末尾。首页另展示少量可直接读懂的实测结论；详细过程继续由已有文章承接。无需以广告审批为理由编造新功能或做无关工具。

## 两条具体用户路径

### 新用户：Windows + PowerShell

首页“第一次安装” → 下载页选择系统与 Shell → 给出已有验证过的安装方法 → 显示 PowerShell 初始化与适用配置文件说明 → 验证二进制与 Shell 函数 → 创建并加入一个测试目录 → 确认实际跳转。主题或插件覆盖 prompt 的例外链接到现有 Windows 实测教程。

验收重点是用户能完成首次跳转，不是页面里出现了几个“zoxide install Windows”。不要把 Bash 的 mkdir、type 或 source 命令直接套给 PowerShell。

### 已安装用户：出现 No match found

首页“已安装但不能用” → 选择实际错误 → 先查看已有记录 → 根据空库、当前目录、关键词顺序或末级目录问题分流 → 给出最小修复 → 再验证 query 和跳转。无需用户通读命令参考或运行一个不相关的安装器。

分步自查第一版可完全由用户选择与已有解释组成；交互只改善定位速度。若以后解析用户粘贴的诊断输出，应本地处理、提醒去除私人路径，并明确推断局限；没有必要为了首版改造新增后端或采集真实配置文件。

## 原创证据如何展示

复用站内已有测试与工具成果：PowerShell 提示符覆盖导致停止学习、fzf 与普通 z 的区别、_ZO_EXCLUDE_DIRS 的匹配边界、目录匹配顺序和当前路径的影响等。

每个关键指南在相关结论附近展示：测试环境和版本、实际命令、预期或观察输出、结论、适用边界、详细来源。原始日志是补充，核心结论不依赖读者跳到大段 JSON 才能理解。保留实际的 10 月测试日期，未重测就不改成 11 月“最新实测”。

“看过资料后改用第一人称”不是原创证据。没有实际运行结果时明确为官方文档说明或待验证建议。作者经历、图片、数据均不能为通过审核而编造。

## 执行顺序与发布边界

1. 将已有三项本地修正整合进本轮变更，不丢弃或重复覆盖；记录线上与候选版本差异。
2. 第一批完成首页、导航、下载页安装路径、排错中心与指南索引分组。先把用户已有内容变得可用，不等待新增大量文章。
3. 第二批完善工具页分步自查与关键页证据展示；以真实可完成任务衡量是否需要交互，而不是机械增加工具数量。
4. 三语同步检查入口、语言标签与落地页。没有足够证据时不批量移除中文/日文，不把多语言本身判作违规。
5. 本地生产构建、桌面/手机预览、路径和配置检查完成后，部署已审查的修改；线上验收确认发布真实生效，才记录为“整改完成”。本文件本身没有执行部署或操作 AdSense。
6. 已被拒审的状态下，修复实际问题、完成线上验收后再通过后台申请审核；不编造必须等待某个固定天数的规定，不反复删除站点重建申请。

## 验收标准

- 陌生用户能从首页立即区分安装、排错、命令查询三个入口。
- Windows/PowerShell 与 macOS/Zsh 等重点组合各自只显示适用的命令；未验证组合有明确范围说明。
- 上述两条用户路径能完成验证，无需在 Blog、Tutorials、FAQ 间来回猜测。
- zoxide-doctor 在主导航或首屏相关区域直接可见；不用 Node 的用户也能执行人工检查路径。
- 关键指南有可核对的实测结论，不能只写“已验证”。
- 原有重要网址、canonical、重定向和 AdSense 配置保留；如确需合并，先做页面与搜索数据判断，再逐条处理跳转。
- 已有 78 URL 作为历史基线比对，不预设必须维持特定数量或扩到特定文章数；sitemap 如实反映最终可索引内容。
- 当前三语选择与站内搜索标签一致；手机无阻碍任务完成的遮挡或横向溢出。
- 明确区分构建成功、本地验证、线上发布、Google 重新抓取和 Google 审批结果，不能互相替代。

## 附件中不能当政策使用的说法

| 说法 | 处理 |

| 90% 的站死于低价值、某项触发即 100% 被拒 | 没有提供可核验样本，不用作风险概率 |
